# QR公開前の確認（2026-09-06）

この確認はリポジトリのコードとSQLが対象。本番環境のDB設定・ネットワーク制御・秘密情報の強度は未確認。侵入テストではない。

## 対応済み

- HTMLのrobotsメタと全ルートのX-Robots-Tagにnoindex, nofollowを指定。
- Referrer-Policy: same-origin、X-Content-Type-Options: nosniff、X-Frame-Options: DENYを追加。
- 管理者セッションはHMAC署名、有効期限、HttpOnly Cookie、本番Secure属性を使用。

## 公開前に必要な対応

1. `supabase/schema.sql`と既存migrationはanon/authenticatedに業務テーブルの全操作を許可している。キーが知られた場合、管理者ログインを迂回できる構成。本番の権限を確認し、サーバー専用キーでAPIからのみアクセスする構成に移行する。サーバー設定の切替前に権限を剥奪すると現在のAPIが動かなくなるため、同時に実施する。
2. 予定POSTは認証なしで同一会社・日付の予定を上書きできる。会社一覧、前回予定、予定集計も入場認証で保護する。画面だけを隠しても保護にならない。
3. ログイン・コード照合・投稿に共有ストレージまたはホスティング側の回数制限を導入する。現状のコードには回数制限がない。サーバーメモリのみの制限は複数インスタンスで不十分。

## 推奨するQR入場方式（未実装）

- 管理者が入場コードを発行・無効化できる。短い識別番号ではなく、暗号学的乱数による十分長いトークンを使用し、DBにはハッシュのみ保存。
- 現場のQRを読み取り、トークンをサーバーで照合したら期限付きHttpOnlyセッションを発行。以降の入力にコードの手入力を求めない。
- QRトークンがURL・アクセスログに残る範囲を抑え、照合後は通常URLへ移動する。入場コード無効化時は発行済みセッションも拒否する設計にする。
- 通常のトップページへのアクセスは入場案内のみ。すべての職人向けAPIでもセッションを検証する。
- 共通QRは利用場所への入場手段であり、個人や会社の本人確認にはならない。QR写真を転送された場合も使える。会社のなりすましまで防ぐなら会社別の認証が必要。

noindexは検索表示を抑える指定であり、アクセス制御ではない。robots.txtで全面クロール禁止にすると検索エンジンがnoindexを読み取れない場合があるため、noindex単体の効果と混同しない。
