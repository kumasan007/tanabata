# 作業予定入力システム 設計メモ

## 決定事項

- 会社マスタと作業予定を含むすべての業務データはSupabaseを唯一の正データ源とする
- Box、SharePoint、OneDriveなどの外部ファイルから会社マスタを同期しない
- Excel／CSVはSupabaseデータの出力・閲覧用途に限定する
- 職人側フォームは完全公開とする
- 現場は1つだけ扱う
- 同じ作業日・同じ一次会社の予定は1件だけ持つ
- 再送信された場合は、既存予定を削除して新しい内容で上書きする
- 1回の送信が、その一次会社のその日の全作業予定を表す
- 1つの一次会社に対して、複数の二次会社を登録できる
- 作業エリアと作業内容は予定グループ全体で1つずつ持つ
- 作業エリアと作業内容は自由入力とする
- 作業なしは協力会社本人が入力する
- 作業なしの場合、来場予定日・作業エリア・作業内容・人数・二次会社は任意入力とする
- 送信後に「同じ内容で別日を入力」できるようにする
- 修正履歴・再送信履歴は残さない
- 職人側フォームの日付入力は、当面は1日だけとする
- APIとDBは、将来の複数日登録再開に備えて期間登録に対応したまま残す
- 人数・作業エリア・作業内容の「前回をコピー」ボタンは、同じ一次会社・同じ作業区分で対象日より前の最新予定の実際の値を入力欄へコピーする
- コピー後も編集でき、編集した項目の「コピー済み」表示を戻す。送信時は画面の値を保存し、前回データを再解決しない
- 一度に一つの質問を表示し、一次会社、日付、作業あり・なしの順に進む。回答済みの質問は非表示にし、「戻る」で修正できる。画面が切り替わると先頭を表示する
- 作業ありでは、日本時間の本日の作業あり予定（なければ本日以前の最新の作業あり予定）を表示して、同じ作業か「はい」「いいえ」で選ぶ。未来日の予定はコピー元にしない。「はい」は一括コピーして確認へ、「いいえ」は人数、作業内容の順に入力する。コピー後も編集でき、過去の作業がない場合や取得失敗時も新規入力できる
- 作業なしでは次回の作業予定を「日付を指定」「未定」から選ぶ。どちらも次に作業エリア・作業内容を任意入力でき、空欄でも確認・送信へ進める。未定は次回日付をnullで保存する
- 二次会社も一次会社と同じ会社名・人数の横並びとし、人数欄の幅をスマートフォン112px、640px以上170pxに揃える。前回人数のコピーは人数欄の下、削除は行の下に配置する
- 引き継ぎ元と送信前の確認では実際の会社名と右揃えの人数、合計人数を表形式で表示し、その下に作業エリア・内容をまとめる。「はい」は濃い緑、「いいえ」は薄い背景色と枠線を付けた同じ大きさのボタンとする
- 日付は「今日」「明日」「明後日」を横並びで表示し、その下の「任意の日付を選ぶ」から別の日を指定する。初期状態では日付を選択しない。一次会社を変更した場合は入力内容をリセットする
- 作業あり・なしとも一次会社と一次会社人数を同じ横並びにし、作業なしの次回来場予定日はその下に表示する
- 入力締め切りによる時刻制限は設けない
- 入力画面は高齢の利用者を想定し、大きな文字・ボタンの1列構成とする。装飾用の見出し・英語コピー・アイコン・ブランド表示は置かない
- 入力画面の一次会社・二次会社は会社マスタからの選択のみとし、会社名の自由入力はさせない。未登録の会社は管理画面で追加する
- 入力画面の人数は初期値・最低値を0とし、入力を消した場合も0に戻す。作業ありの場合は従来どおり一次・二次会社の合計人数を1人以上とする
- 管理画面の件数表示は一覧に対応する「予定件数」に統一する。予定行全体や内訳ボタンでは開閉せず、日付のクリックで開閉する。会社名・人数・エリア・内容はクリックで値だけをコピーできる
- 管理画面のCSV・Excelダウンロード操作は当面表示しない。既存の出力APIとExcelフィードは保持する

## データフロー

```text
職人入力画面 ─┐
管理画面     ─┼─> Next.js API routes ─> Supabase PostgreSQL
Excel出力    <┘
```

- ブラウザからの業務データ操作はNext.js API routesを経由する
- APIは `SUPABASE_URL` と `SUPABASE_ANON_KEY` でSupabaseへ接続する
- 会社マスタ・作業予定ともに外部サービスからの取込や同期は行わない
- Excel／CSVフィードはSupabaseからの一方向出力とする

## DB設計案

### company_master

一次会社・二次会社の選択肢です。Supabaseを正データとし、管理画面から編集します。

| column | type | note |
| --- | --- | --- |
| id | uuid | primary key |
| primary_company | text | 一次会社名 |
| secondary_company | text | 二次会社名。空欄可 |
| sort_order | integer | 入力画面と管理画面での表示順 |

一次会社・二次会社の組み合わせには重複防止インデックスを設定します。

- 一次会社1社に対する複数の二次会社を一括登録できる
- 一覧の上下ボタンで並び替え、自動保存する。一次会社は配下の二次会社と一緒に移動し、二次会社は同じ一次会社内で並び替える
- 作業予定確認の会社フィルターはプルダウンで選択し、一次会社変更時に二次会社の選択を解除する
- 既存の組み合わせは重複登録せず、新しい二次会社だけを追加する

### schedule_groups

一次会社単位の予定グループです。

| column | type | note |
| --- | --- | --- |
| id | uuid | primary key |
| work_date | date | 作業日 |
| status | text | `work` または `no_work` |
| primary_company | text | 一次会社名。会社マスタの表記をそのまま保存 |
| primary_count | integer | 一次会社人数 |
| work_area | text | 作業エリア |
| work_content | text | 作業内容 |
| next_visit_date | date | 任意 |
| next_primary_count | integer | 任意 |
| next_work_content | text | 任意 |
| created_at | timestamptz | 作成日時 |
| updated_at | timestamptz | 更新日時 |

unique制約:

```sql
unique (work_date, primary_company)
```

### schedule_subcompanies

予定グループに紐づく二次会社人数です。

| column | type | note |
| --- | --- | --- |
| id | uuid | primary key |
| schedule_group_id | uuid | schedule_groups.id |
| kind | text | `current` または `next_visit` |
| secondary_company | text | 二次会社名。空欄も許容 |
| worker_count | integer | 人数 |
| sort_order | integer | 表示順 |

`kind = current` は作業ありの当日二次会社、`kind = next_visit` は作業なし時の次回来場予定二次会社として扱います。

## 上書きフロー

`POST /api/schedules` で登録します。

1. 入力値をサーバー側で検証する
2. `work_date + primary_company` に一致する既存 `schedule_groups` を検索する
3. 既存があれば、紐づく `schedule_subcompanies` を削除する
4. `schedule_groups` をupsertする
5. 新しい `schedule_subcompanies` をinsertする

履歴は残さない前提のため、削除して差し替える設計にします。

## 複数日登録

現在の職人側フォームでは単日入力だけ表示します。

内部APIは開始日から終了日までの日付をサーバー側で展開し、日付ごとに `schedule_groups` を作成できる構造のまま残します。

期間入力を復活させる場合、土日除外は任意チェックにします。建設現場では土曜作業があるため、初期値は除外しません。

## 送信後の別日入力

送信完了後に以下のボタンを出します。

- 同じ内容で別日を入力
- 新しく入力する

`同じ内容で別日を入力` は、会社・人数・作業内容・作業エリアを保持し、日付だけ変更可能な状態に戻します。

## Excel出力

Web管理画面のダウンロード操作は当面非表示です。以下は保持している出力APIの仕様です。

Excelは正データではなく、Supabaseに保存された予定の閲覧・受け渡し用です。Excel側で変更した内容をSupabaseへ戻す同期処理は持ちません。

- 日付ごとにシートを分ける
- 二次会社ごとに1行出力する
- 二次会社なしの場合は二次会社欄を空欄で1行出力する
- 作業なしで来場予定の二次会社が複数ある場合は、来場予定二次会社ごとに1行出力する

列定義:

| 列 | 項目 |
| --- | --- |
| A | 作業日 |
| B | 予定 |
| C | 一次会社 |
| D | 一次会社人数 |
| E | 二次会社 |
| F | 二次会社人数 |
| G | 作業エリア |
| H | 作業内容 |
| I | 来場予定日 |
| J | 来場予定一次会社人数 |
| K | 来場予定二次会社 |
| L | 来場予定二次会社人数 |
| M | 来場予定作業エリア |
| N | 来場予定作業内容 |
| O | 登録日時 |
| P | 更新日時 |

マスタExcel側では、取込時に以下を追加します。

| 列 | 項目 |
| --- | --- |
| Q | 取込日時 |
| R | 取込元ファイル |

## 会社マスタ取得

`GET /api/companies` でSupabaseの `company_master` を取得します。

- ブラウザからSupabaseへ直接アクセスせず、Next.js API routesを経由する
- 取得に失敗した場合はフォームにエラーを表示する
- 0件の場合は空の会社マスタとして扱う
- 会社名は正規化しない

## 後から変えると影響が大きい点

- 複数現場対応を追加する場合、ほぼ全テーブルに `site_id` が必要になる
- `work_date + primary_company` 上書きから履歴管理へ変える場合、unique制約と管理画面の見せ方を変える必要がある
- 作業エリア・作業内容を二次会社ごとに持たせる場合、テーブル構造とExcel出力が変わる
- 作業なし時の来場予定を複数日持たせる場合、来場予定専用テーブルが必要になる
- Excel側を正データにする運用へ変える場合、Web DBとの同期設計が必要になる
